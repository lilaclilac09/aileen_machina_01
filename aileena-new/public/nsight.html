SOLUTIONS  What to optimize next

Why: two hot stages, two diseases — stage 02 moves too many bytes, stage 04 has too few tiles.

DO THIS
  1. Measure first: nsys + ncu, replace every estimate on this page.
  2. Skinny GEMM + adaptive Split-K — 18 tiles → 100+.
  3. FP8 precision gate — pass tolerance before touching bytes.
  4. Single-FP8 reads — 188 → 94 MiB, pooler + unpooler first.
  5. Router fusion + CUDA Graph — x read once, launches replayed.
  6. Prefetch + WGMMA/TMA — only if ncu proves DRAM full, SMs idle.
DO NOT
  • Do not tune GEMM tiles at small m — the math is 3 µs.
  • Do not expect FP8 hi+lo to save bandwidth — it saves nothing.
  • Do not touch the m ≥ 192 path — it already beats baseline.

SOLUTIONS  What to optimize next

Why: every token re-streams the entire KV cache — the read grows with L, the math does not.

DO THIS
  1. Split-KV (Flash-Decoding) — split L across blocks, stream in parallel.
  2. Paged KV layout — appends O(1), reads sequential.
  3. FP8 KV cache — halves the stream, same gate as bf16 step 3.
  4. CUDA Graph — the step repeats identically per token.
DO NOT
  • Do not tune the attention math — it is 15%.
  • Do not split L without online softmax — partials will not merge.
